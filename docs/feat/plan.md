# PiggyBack — 사이트 기획 및 구현 스펙

> 부산 방문 외국인 관광객을 위한 다국어 장소 해석(resolution) 서비스
> 문서 버전 v0.1 · 작성일 2026-08-15 · 구현 위임용 스펙

---

## 0. 이 문서를 읽는 법

이 문서는 **로컬 AI 에이전트가 그대로 구현할 수 있는 수준**으로 작성되었다.
"적절히", "예쁘게", "필요에 따라" 같은 표현은 의도적으로 배제했다. 값이 정해지지 않은 항목은 §10 미결 사항에 모아두었고, 그 항목들은 임의로 채우지 말고 결정을 받은 뒤 진행한다.

구현 우선순위는 다음과 같다.

1. 검색 해석 엔진 (§4) — 제품의 전부
2. 결과 화면 (§3.2) — 실사용 트래픽의 대부분이 도달하는 곳
3. 홈 화면 (§3.1) — 신뢰와 브랜드
4. 이벤트 화면 (§3.3)

## 1. 제품 정의

### 1.1 해결하는 문제

외국인 관광객이 부산의 장소를 검색할 때, **한국어 발음을 정확히 알아야만 검색이 된다.**

`Haeundae`는 검색되지만 `hey oon day`, `해운대` 발음을 들은 대로 옮긴 `ヘウンデ`, 자국 표기인 `海云台`로는 원하는 결과에 도달하지 못하거나, 검색 엔진마다 결과가 달라진다. 여행자는 자기가 아는 표기로 검색할 뿐인데, 그 표기가 시스템이 기대하는 형태와 어긋난다.

PiggyBack은 이 간극을 메운다. **대충 친 걸 알아듣고, 정확한 장소로 업어서 데려다준다.**

### 1.2 한 문장 정의

> 어떤 언어로 어떻게 적어도 부산의 장소를 찾아주고, 거기 가는 법과 지금 열리는 이벤트를 알려주는 서비스.

### 1.3 핵심 가치 — 단 하나의 순간

이 제품에는 마법 같은 순간이 정확히 하나 있다.

**"내가 대충 친 걸 얘가 알아들었다"** 는 그 찰나.

`hey oon day` → `해운대` 로 수렴하는 순간이 제품의 전부다. 지도도, 사진도, 정보량도 아니다. 디자인·모션·카피의 예산 전부를 이 한 순간에 집중한다. 나머지 화면은 조용하고 빠르면 된다.

### 1.4 무엇이 아닌가 (Non-goals)

명시적으로 하지 않는 것들이다. 구현 중 "이것도 있으면 좋겠는데" 판단으로 추가하지 않는다.

- **예약·결제 없음.** 외부 예약처로 링크만 보낸다.
- **로그인·회원가입 없음.** 모든 기능은 비로그인으로 동작한다.
- **자체 내비게이션 없음.** 경로 안내는 Google Maps / Naver Map / 카카오맵 딥링크로 위임한다. 지도 SDK를 직접 붙여 턴바이턴을 구현하지 않는다.
- **자유 대화형 챗봇 아님.** 봇은 **정해진 물음(fixed intent)** 만 처리한다. §6 참조.
- **부산 외 지역 없음.** 전국 확장은 이 버전의 고려 대상이 아니다.
- **후기·평점·UGC 없음.**

## 2. 사용자 진입 경로

### 2.1 실제 트래픽 구조

주 진입점은 봇(메신저)이다. 이 전제가 사이트 구조를 결정한다.

```
[메신저 봇] --(딥링크)--> /place/{id}   ← 트래픽의 대부분
[검색엔진/QR] ----------> /            ← 신규 유입
[봇 또는 홈] -----------> /events       ← 탐색
```

**따라서 이 사이트의 본체는 홈이 아니라 결과 페이지다.**

- 홈(`/`)의 역할: 봇 밖에서 들어온 사람 받기 + "제대로 된 서비스구나"라는 신뢰 주기
- 결과(`/place/{id}`)의 역할: 3초 안에 필요한 답 주기

홈은 예뻐야 하고, 결과는 빨라야 한다. 성능 예산도 이 순서를 따른다.

### 2.2 필수 전제

- **모바일 우선은 선택이 아니라 전제다.** 메신저 인앱 브라우저에서 열리므로 실사용의 거의 전부가 모바일이다. 데스크톱은 반응형으로 깨지지 않는 수준이면 충분하고, 데스크톱 전용 레이아웃에 시간을 쓰지 않는다.
- 인앱 브라우저(LINE / WhatsApp / WeChat 내장 웹뷰)에서 동작을 검증한다. 이들 웹뷰는 일부 최신 CSS와 폰트 로딩 동작이 표준 브라우저와 다르다.
- 첫 화면 유의미 렌더까지 **2초 이내** (4G, 중급 안드로이드 기준).

## 3. 화면 명세

원래 구상은 검색·이벤트 2개 화면이었으나, 봇이 주 진입점인 이상 **결과 화면은 별도 라우트로 반드시 필요하다.** 공유 가능한 URL이 없으면 봇이 링크를 보낼 수 없다.

| 라우트 | 이름 | 단 하나의 목적 |
|---|---|---|
| `/` | 검색 | 아무 표기로나 쳐도 찾아준다는 걸 3초 안에 납득시킨다 |
| `/place/{id}` | 결과 | 여기가 맞는 곳인지 확인시키고, 가는 법을 준다 |
| `/events` | 이벤트 | 지금 부산에서 뭐가 열리는지 훑게 한다 |
| `/events/{id}` | 이벤트 상세 | 이벤트 정보 + 장소로 연결 |

### 3.1 `/` 검색

```
┌─────────────────────────────────┐
│  PIGGYBACK              [ 언어 ]│
│                                 │
│  Type it however                │
│  you heard it.                  │
│                                 │
│  ┌───────────────────────────┐  │
│  │ hey oon day             ⌕ │  │  ← 히어로 = 검색창
│  └───────────────────────────┘  │
│                                 │
│  ┌ ─ 환적 스트립 ─────────────┐ │
│  │ IN   hey oon day    [ en ] │ │  ← 시그니처
│  │ ─────────────────────────  │ │
│  │ OUT  해운대                │ │
│  │      Haeundae  ヘウンデ    │ │
│  │      海云台                │ │
│  └───────────────────────────┘ │
│                                 │
│  Others are looking for         │
│  ┌────┐ ┌──────┐ ┌────────┐    │
│  │감천 │ │ 자갈치│ │ 광안리 │    │  ← 다국어 혼용 칩
│  └────┘ └──────┘ └────────┘    │
└─────────────────────────────────┘
```

**요소별 명세**

- **검색 입력** — 히어로 전체를 차지한다. 페이지 로드 시 자동 포커스하지 않는다(모바일에서 키보드가 즉시 올라와 화면을 덮는다). 대신 탭 영역을 크게 잡는다.
- **환적 스트립** — 입력 중 실시간으로 해석 결과를 보여준다. 이 사이트의 시그니처 요소. 상세는 §5.4.
- **인기 검색 칩** — 각기 다른 언어 표기로 섞어서 노출한다. 목적은 트렌드 전달이 아니라 **"저렇게 쳐도 되는구나"를 학습시키는 것**이다. 8개 고정, 서버에서 주입.
- **언어 선택** — 우상단. 자동 감지된 값을 기본으로 하되 항상 수동 변경 가능해야 한다. 자동 감지만 믿고 선택지를 숨기지 않는다.

카피 원칙: 제품 설명 문장을 쓰지 않는다. 환적 스트립이 동작하는 것 자체가 설명이다.

### 3.2 `/place/{id}` 결과

봇 링크의 도착지. **정보 밀도보다 확인 속도**가 우선이다. 여행자가 이동 중에 한 손으로 본다.

```
┌─────────────────────────────────┐
│ ← Haeundae Beach                │
│   해운대해수욕장                 │  ← 한글 병기: 택시 기사에게 보여주는 용도
│   ヘウンデ / 海云台               │
│                                 │
│ [ 대표 이미지 ]                  │
│                                 │
│ ◆ 지금 열려 있음 · 24시간        │  ← 상태 먼저
│                                 │
│ ── 가는 법 ──────────────────    │
│ 지하철 2호선 해운대역 3번 출구    │
│ 도보 10분                        │
│ [ Google Maps ] [ Naver Map ]    │
│                                 │
│ ── 여기서 열리는 이벤트 ──────    │
│ · 부산바다축제  8.1–8.9          │
│                                 │
│ ── 설명 ────────────────────     │
│ ...                              │
└─────────────────────────────────┘
```

**설계 원칙**

- **한글 명칭을 크고 선택 가능하게 표시한다.** 여행자가 택시 기사·행인에게 화면을 보여주는 것이 실제 사용 시나리오다. 이건 장식이 아니라 기능이다. 길게 눌러 복사 가능해야 하고, 이미지로 렌더링하지 않는다.
- **영업 상태를 최상단에** 둔다. "지금 열려 있는가"가 이동 중 여행자의 첫 질문이다.
- 외부 지도 앱 딥링크는 좌표 기반으로 생성한다. 앱 미설치 시 웹으로 폴백된다.

### 3.3 `/events` 이벤트

여기는 사진 없이는 성립하지 않는 화면이므로, 검색 화면과 달리 **에디토리얼 매거진 그리드**로 간다. 비대칭 그리드, 큰 타이포, 이미지 위 텍스트 오버레이.

두 화면의 톤 차이는 **동일한 타입 스케일과 동일한 여백 규칙**으로 묶는다. 그러면 색과 밀도가 달라도 한 몸으로 읽힌다.

```
┌─────────────────────────────────┐
│ Happening now                    │
│ ┌─────────────────────────────┐ │
│ │ [       대형 이미지        ] │ │  ← 진행 중 1건 피처
│ │  부산바다축제                │ │
│ │  Aug 1–9 · Haeundae          │ │
│ └─────────────────────────────┘ │
│                                 │
│ Coming up                       │
│ ┌──────────┐ ┌──────────┐      │
│ │ [이미지] │ │ [이미지] │      │  ← 2열 그리드
│ │ 불꽃축제 │ │ BIFF     │      │
│ └──────────┘ └──────────┘      │
└─────────────────────────────────┘
```

- 정렬 기준: 진행 중 → 임박 순. 과거 이벤트는 노출하지 않는다.
- 이미지가 없는 이벤트는 §5.3의 타이포그래피 폴백 카드를 쓴다. 회색 플레이스홀더 박스를 쓰지 않는다.

## 4. 검색 해석 엔진 — 이 제품의 심장

**사이트는 단순하다. 어려운 건 전부 여기 있다.** 이 부분의 정확도가 곧 제품의 가치이므로, UI보다 먼저 그리고 더 많이 투자한다.

### 4.1 단계별 폴백 구조

LLM부터 시작하지 않는다. 비용·지연·불확실성이 모두 크고, 실제로는 아래 2단계에서 대부분 해결된다.

**1단계 — 정규화**
소문자화, 공백·하이픈·아포스트로피 제거, 유니코드 NFD 분해 후 발음 구별 기호 제거, 전각→반각 변환.
`Hae-un-dae` / `haeundae` / `HAEUNDAE` → `haeundae`

**2단계 — 별칭 사전 (수기 큐레이션) ★ 최우선 구현**
부산 상위 300개 POI에 대해 언어별 표기 변형을 손으로 정리한 사전. 
**실제 검색 질의의 90% 이상이 여기서 해결된다.** 구현 비용이 가장 낮고 효과가 가장 크다.

```json
{
  "id": "haeundae-beach",
  "ko": "해운대해수욕장",
  "aliases": {
    "en": ["haeundae", "haeundae beach", "hae un dae", "hey oon day", "heundae"],
    "ja": ["ヘウンデ", "海雲台", "ヘウンデビーチ"],
    "zh-Hans": ["海云台", "海云台海水浴场"],
    "zh-Hant": ["海雲台"],
    "th": ["แฮอุนแด"]
  }
}
```

오탈자 변형까지 포함시킨다. 실사용 로그를 보고 계속 추가하는 것이 이 사전의 운영 방식이다.

**3단계 — 로마자 역변환**
국어의 로마자 표기법(RR), 매큔-라이샤워(MR), 관용 표기 세 가지를 모두 시도해 한글 후보를 생성한다. 여권·도로표지·구글 지도가 서로 다른 체계를 쓰기 때문에 하나만 지원하면 안 된다.

**4단계 — 음성학적 근사 매칭**
한글 자모 단위로 분해한 뒤 편집 거리(Levenshtein)를 계산한다. 임계값 이내 후보를 신뢰도 순으로 반환.

**5단계 — 의미 검색 폴백**
1~4단계가 모두 실패했을 때만 임베딩 유사도 또는 LLM 호출로 넘어간다. 여기서 성공한 질의는 **자동으로 로그에 남기고 2단계 사전 보강 후보로 큐에 넣는다.** 같은 질의가 두 번 5단계로 가면 안 된다.

### 4.2 응답 계약

해석 결과는 항상 신뢰도와 함께 반환한다. UI는 신뢰도에 따라 다르게 동작한다.

```ts
type Resolution = {
  query: string;
  detectedLang: string;
  stage: 1 | 2 | 3 | 4 | 5;   // 어느 단계에서 해결되었는가
  matches: Array<{
    placeId: string;
    nameKo: string;
    nameLocalized: string;
    romanized: string;
    confidence: number;        // 0.0 – 1.0
  }>;
};
```

| 신뢰도 | UI 동작 |
|---|---|
| ≥ 0.9, 단일 후보 | 결과 페이지로 바로 이동 |
| ≥ 0.6 | 환적 스트립에 표시 + 확인 대기 |
| < 0.6 | "이거 말씀하신 건가요?" 후보 목록 제시 |
| 후보 없음 | §5.5 빈 상태 |

## 5. 디자인 방향

### 5.1 컨셉 — 환적(換積, Transshipment)

부산은 세계 최대급 환적항이다. 화물이 한 배에 실려 와서 다른 배로 옮겨 실려 나간다. **Piggyback은 원래 화물 용어다** — 트레일러를 화차에 통째로 얹어 나르는 복합운송 방식(TOFC)을 뜻한다. 이름과 도시가 같은 세계관을 공유한다.

이 사이트는 **단어에 대해 같은 일을 한다.** 당신의 언어가 들어와서, 한국어로 옮겨 실리고, 당신은 그걸 타고 목적지에 도착한다.

컨테이너 야드, 적하목록, 크레인, 해무. 여기서 색과 질감을 가져온다.

**"부산 = 바다 = 파랑"은 쓰지 않는다.** 부산 관련 사이트가 전부 파랑이라 차별화가 되지 않고, 이 제품의 본질(언어 해석)과도 무관하다. 팔레트에 파랑 계열을 넣지 않는다.

### 5.2 디자인 토큰

```css
:root {
  /* Color */
  --ink:       #14181A;  /* 강철 흑색. 본문, 헤드라인 */
  --fog:       #E9EBE6;  /* 해무. 기본 배경 (크림 아님 — 차가운 녹회색) */
  --paper:     #F7F8F5;  /* 카드 표면 */
  --signal:    #FF4D14;  /* 컨테이너 오렌지. 해석 결과 강조 — 유일한 강한 색 */
  --verdigris: #2E6B5C;  /* 산화 구리. 상태·이벤트 라벨 */
  --steel:     #9AA3A0;  /* 보조 텍스트, 구분선 */

  /* Type scale — 1.333 (Perfect Fourth) */
  --t-display: 3.25rem;
  --t-h1:      2.0rem;
  --t-h2:      1.5rem;
  --t-body:    1.0625rem;  /* 다국어 혼용 가독성 위해 16px보다 크게 */
  --t-mono:    0.875rem;
  --t-caption: 0.8125rem;

  /* Spacing — 8px base */
  --s-1: 0.5rem;  --s-2: 1rem;   --s-3: 1.5rem;
  --s-4: 2rem;    --s-6: 3rem;   --s-8: 4rem;

  --radius: 2px;  /* 거의 각진 형태. 컨테이너·적하목록의 직각 */
}
```

`--signal` 오렌지는 **해석이 성공한 지점에만** 쓴다. 버튼, 링크, 헤더에 남발하면 시그니처가 죽는다. 화면당 1~2회 이하.

### 5.3 타이포그래피

**다국어가 이 프로젝트의 가장 큰 타이포 제약이다.** 영어·일본어·번체·간체·태국어가 한 화면에 섞인다. 라틴 전용 디스플레이 폰트를 먼저 고르고 시작하면 나중에 전부 갈아엎게 된다.

| 역할 | 폰트 | 용도 |
|---|---|---|
| Display | **Archivo Expanded** 700/800 | 워드마크, 라틴 히어로 문구 전용 |
| Display (KO/CJK) | **Pretendard** 800, letter-spacing −0.02em | 한글·CJK 큰 제목 |
| Body / UI | **Pretendard** 400/600 | 본문 전반 |
| Mono | **JetBrains Mono** 400/700 | 환적 스트립, 코드성 정보 |

폴백 체인:
```css
font-family: "Pretendard", "Noto Sans JP", "Noto Sans SC",
             "Noto Sans TC", "Noto Sans Thai", sans-serif;
```

Archivo Expanded는 한글을 지원하지 않는다. **라틴 문자열이 확실한 곳에만** 쓰고, 나머지는 Pretendard 800으로 처리한다. 개성은 폰트 자체가 아니라 **크기·굵기·자간 대비**로 만든다.

Mono를 환적 스트립에 쓰는 것은 장식이 아니라 기능이다. 고정폭이라 입력 문자와 출력 문자가 세로로 정렬되어 대응 관계가 눈에 보인다. 동시에 적하목록(manifest)의 인상을 준다.

### 5.4 시그니처 요소 — 환적 스트립

이 사이트가 기억될 단 하나의 요소. 검색창 바로 아래, 적하목록 한 줄처럼 생겼다.

```
┌────────────────────────────────────────┐
│ IN    hey oon day                 [en] │
│ ─────────────────────────────────────  │
│ OUT   해운대                           │  ← --signal 오렌지
│       HAEUNDAE   ヘウンデ   海云台      │  ← --steel
└────────────────────────────────────────┘
```

**동작 사양**

- 입력 200ms 디바운스 후 해석 요청
- 결과 도착 시 `OUT` 행의 한글이 **좌→우로 문자 단위 순차 등장** (문자당 24ms, 총 최대 200ms)
- 감지 언어 배지는 `IN` 행 우측에서 페이드 인
- 해석 실패 시 `OUT` 행은 `--steel` 색의 점선 플레이스홀더를 유지한다. 붉은 오류 색을 쓰지 않는다 — 아직 입력 중일 수 있다.
- `prefers-reduced-motion: reduce` 에서는 순차 등장 없이 즉시 표시

**모션은 여기에만 쓴다.** 스크롤 리빌, 페이지 전환 효과, 호버 파티클 등을 추가하지 않는다. 시그니처 하나만 움직이고 나머지가 정적일 때 그 하나가 산다.

### 5.5 빈 상태 · 오류 상태

빈 화면은 분위기를 잡는 자리가 아니라 **다음 행동을 안내하는 자리**다.

| 상황 | 표시 |
|---|---|
| 해석 실패 | "That one's not in our yard yet." + 인기 장소 6개 칩 제시 |
| 네트워크 오류 | "Couldn't reach the server. Tap to retry." + 재시도 버튼 |
| 이벤트 없음 | "Nothing on until {다음 이벤트 날짜}." + 해당 이벤트로 링크 |
| 이미지 없음 | 회색 박스 대신, 장소명을 Display 폰트로 크게 배치한 타이포 카드 |

오류 문구는 사과하지 않고, 무엇이 일어났고 무엇을 하면 되는지만 말한다.

### 5.6 카피 원칙

- 영어 기본, 문장부호 최소, 문장 형태(sentence case)
- 버튼은 실행 결과를 그대로 말한다: "Show on map" (○) / "Submit" (×)
- 같은 동작은 전 화면에서 같은 단어를 쓴다
- 시스템 용어를 노출하지 않는다: "Search failed" (×) / "We couldn't find that" (○)
- 다국어 번역 시 **문자열 길이가 영어의 2배까지 늘어날 수 있음**을 전제로 레이아웃을 잡는다 (특히 독일어·태국어). 고정 너비 버튼 금지.

## 6. 봇 인터페이스

봇은 **정해진 물음만** 처리한다. 자유 대화를 지원하지 않는다.

### 6.1 인텐트 목록

| 인텐트 | 트리거 예 | 응답 |
|---|---|---|
| `RESOLVE_PLACE` | 아무 표기의 장소명 | 해석 결과 + `/place/{id}` 링크 |
| `HOW_TO_GET` | "how do I get there" | 대중교통 요약 + 지도 딥링크 |
| `WHATS_ON` | "what's happening" | 진행 중 이벤트 3건 + `/events` 링크 |
| `NEARBY` | "near me" | 좌표 요청 → 인근 POI 5건 |
| `FALLBACK` | 그 외 전부 | 위 4개 버튼 제시 |

### 6.2 원칙

- 봇 응답에는 **항상 웹 링크를 포함한다.** 봇은 라우터, 웹이 본체다.
- 링크에는 `?ref=bot&lang={감지언어}` 를 붙여 유입 경로를 추적한다.
- 해석 신뢰도가 0.6 미만이면 봇이 후보 3개를 버튼으로 제시한다. 추측해서 단정하지 않는다.

## 8. 기술 전제

> 아래는 기존 스택을 따른 가정이다. 다르면 §10에서 확정할 것.

- Next.js (App Router) + TypeScript
- 스타일: Tailwind CSS + §5.2 토큰을 CSS 변수로 주입
- 외부 API 호출은 **전부 서버 라우트를 경유한다.** API 키를 클라이언트에 노출하지 않으며, 공공 API의 트래픽 쿼터를 서버에서 통제한다. (<cite index="41-1">축제 API 개발계정 기준 10,000건 제한</cite>)
- 라우팅: `/[lang]/...` 경로 기반 i18n. 쿠키 기반 언어 분기는 캐시와 충돌하므로 쓰지 않는다.
- 렌더링 전략
  - `/` — 정적 (검색은 클라이언트에서 API 호출)
  - `/place/{id}` — ISR. **봇 링크가 SNS 프리뷰로 펼쳐지므로 OG 태그가 서버에서 렌더되어야 한다.**
  - `/events` — ISR 1시간

### 품질 하한선 (별도 언급 없이 지킨다)

- 모바일 360px까지 깨지지 않음
- 키보드 포커스 링 가시
- `prefers-reduced-motion` 존중
- 본문 대비비 4.5:1 이상 (`--steel` 을 본문에 쓰지 말 것)
- 이미지 `alt` 다국어 대응

## 10. 미결 사항 — 결정 필요

구현 착수 전 답이 필요한 항목이다. 임의로 정하지 않는다.

1. **지원 언어 확정** — 영/일/중간/중번 4개인가, 태국어·베트남어를 포함한 6개인가? 후자면 §7.2대로 자체 사전 구축 비용이 발생한다.
2. **별칭 사전 초기 규모** — 300건 기준으로 작성했다. 상위 몇 개 POI까지 커버할 것인가?
3. **이벤트 다국어 원천** — 축제 API에 외국어 엔드포인트가 있는가? 없다면 번역을 사람이 하는가, 기계 번역인가?
4. **이미지 라이선스** — 이벤트 화면은 사진 품질에 전적으로 의존한다. 공공 API 제공 이미지의 상업적 이용 범위 확인 필요.
5. **봇 플랫폼** — LINE / WhatsApp / WeChat 중 어디부터인가? 링크 프리뷰 사양이 플랫폼마다 달라 OG 태그 설계에 영향을 준다.
6. **기술 스택 확정** — §8의 Next.js 가정이 맞는가?
7. **도메인·브랜드 표기** — 로고 워드마크를 `PIGGYBACK`으로 전부 대문자 처리할 것인가, `Piggyback`인가?
